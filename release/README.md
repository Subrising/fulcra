# Single-checkout candidate release

Product source lives at the repository root and control source at `control/`. Control retains its own package.json and lockfile and is deliberately **not** a root npm workspace: packaging compiles its sources against the product SDK/dependencies, and adding its independent dependency graph to the product workspace would change dependency resolution. No install is done by these wrappers.

Copy `local/release.env.example` to ignored `local/release.env`, then replace placeholders. `FULCRA_RELEASE_CONFIG` selects another trusted configuration file. The wrappers resolve repository and control paths from their own location; runtime ORCA/PASEO environment identities remain unchanged. `scripts/orca/bootstrap.mjs install` now clones one local consolidated checkout and aliases runtime/conversation/workspace to its `control/` tree, recording one SHA for all components. `--source` selects another consolidated source; explicit legacy component overrides remain supported. The low-level build entry points default to `control/` and still accept their explicit controller argument or `FULCRA_CONTROL_ROOT` override.

The candidate-8 build sequence was brought forward from package-u8.sh, including isolated caches, build configuration generation and resource sampling. Run `release/package.sh --dry-run` on the reviewed clean commit first. `release/package.sh` uses the configured heavy-lock runner and refuses output reuse and insufficient disk space. Its runner adapter must accept `<lock-path> <command> [args...]` and hold the existing scheduler lock for the whole command. `--under-lock` is the internal callback, used only by that adapter. The build remains unsigned as in the original candidate pipeline; signing, notarization, live cutover and publishing require their separately reviewed owner procedures.

The build receipt freezes `repoCommit`, `productCommit`, `controlCommit` and legacy `heads.product`/`heads.control` to the same SHA before generators run. `REQUIRED_ANCESTORS` replaces hardcoded fold ancestry checks; the expected single repository SHA replaces the two remote head checks. No network lookup is needed. There was no `rc_candidate` or productCommit/controlCommit implementation in the imported base; the existing handoff used `heads` instead. These fields are retained and the new aliases added for later consumers.

After packaging, `release/scan-and-seal.sh` performs the original packaged audit, tsbuildinfo absence check, adapter baseline comparison, client manifest pin check and bundle diff. It imports the original seal algorithm locally. Reviewed baselines, reviews and previous handoffs are configuration inputs; evidence is local output. `release/release-zip.sh` creates a new archive, unpacks into an owned temporary directory and requires its seal to match `EXPECTED_BUNDLE_SHA`.

`release/gates.sh` executes the owner-reviewed gate driver under the same scheduler lock. The candidate-9 gate owner must adapt its driver to consume `REPO_ROOT`, `CONTROL_ROOT`, `PRODUCT_ROOT`, `CANDIDATE_APP`, `PREVIOUS_APP`, `EVIDENCE_DIR`, `NODE_BIN`, `PYTHON_BIN`, `PROBE_CLIENT`, `TESTDEVICE_CLIENT`, and any local host/pin settings. Product and control provenance now share one SHA. Point `GATE_DRIVER` at that adapted driver; gate semantics belong to the gate owner.

`release/gates-8.sh` preserves the candidate-8 command list and arguments, using configured fixture/operator directories and paths. It is a compatibility runner: the legacy fixtures still need the gate owner's separate path/config port before they are suitable for a machine-independent checkout. Candidate-9 fixture code is not frozen or duplicated here. Do not infer a passed candidate-9 gate from a dry run or syntax check.

`release/control-suites.sh` discovers tracked control test files from the repository root (important after subtree import) and runs them one at a time through the existing control host loader with a timeout. `TEST_HOST` must be an already built adapter. It returns failure when any test exits nonzero. All scripts support `--help` without reading local config. No commands here install, publish, push or touch live services automatically.
