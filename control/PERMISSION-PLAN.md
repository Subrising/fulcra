# Routine permission handling

The missing loop is an actual native permission prompt, a scoped authorized response, resumed work and an independently reviewed output without a user nudge. Reuse the existing controller journal, native admission guard, event observer and private phone interface.

## Authority and scope

An explicit operator grant enables `owned-files-v1` for an unchanged delegated session generation. It permits at most 100 one-time Claude Write/Edit responses, each input and resulting file at most 256 KiB, inside that session's unique canonical `control-runtime/tasks/<UUID>` folder. The policy rejects hidden path components, symlinks, hard-linked existing files, nonregular files, unknown input fields, edits without one exact match, replace-all edits, shell commands, plan/mode changes, permission-setting updates and all other request kinds. Existing native sandbox and tool settings stay in force. This is a bounded permission policy, not an OS sandbox against the trusted same-user shell, and cannot eliminate filesystem changes after native admission.

The private interface exposes grant/revoke/status with the scope and remaining allowance. Granting a supervisor also allows its newly created workers to inherit the same bounded policy in each worker's separate owned folder, with a binding to the supervisor grant. The 100-response allowance is one shared root pool across the supervisor and all inherited workers, displayed as shared remaining capacity. Each dispatched intent reserves one slot permanently, including uncertain or refused responses; retries do not reset the quota. Root revocation, exhaustion or epoch rotation invalidates inherited intents. Existing workers need an explicit grant. If inheritance fails after a new worker is created, the worker remains ready without routine authority and the interface exposes that limitation. Takeover, re-delegation, grant revocation, supervisor authority changes and native reboot invalidate old permissions; no policy silently survives them. Discovery and inbox acknowledgment grant nothing.

## Native linearization and recovery

Persist separate permission grants and intents in additive journal tables. Each intent binds exact request ID and canonical request digest, exact one-time response, original delegated delivery, worker generation and boot, parent/link/grant epochs where applicable, and native human-input barrier. Distinct request IDs and changed bodies remain distinct evidence. A runtime-only handler inspects current authority and the policy, persists an intent, then calls the supported native response API using an Fulcra-marked request ID. No language-model polling is needed for routine writes.

Patch the native manager's central response method synchronously before provider invocation. Human responses update the existing in-memory human barrier and remain available without reading the journal. Any human permission action, message, stop or cancellation that clears pending requests ends automation for that generation; the interface explains that consequence. Existing human message/stop hooks and the new response hook raise the barrier before automated admission. The native guard remains read-only: automated responses validate the actual pending request, generation, boot, authority, reserved root-quota slot and exact controller-computed scope/response bindings, then synchronously add the request identity to a bounded per-boot in-memory one-shot set before provider invocation. It performs no SQLite write or task-file scan. Set saturation refuses automation while retaining human input. The controller remains the sole journal writer. It persists intent before dispatch and uses the pinned DaemonClient respondToPermissionAndWait API. The native session emits an Fulcra-marked agent_permission_resolved receipt only after the provider response handler completes; the controller requires the matching session, intent and allow response before recording acknowledged. The stock fire-and-forget API is insufficient. Request hashing uses the same sanitized projection as the released Paseo wire payload. Refusal and missing or failed acknowledgment remain separate outcomes. A second response never replays a consumed request; reboot clears the set but invalidates all old boot-bound intents. Provider response failure or a lost reply is uncertain, not a reason to retry; controller restart preserves that uncertainty. Both acknowledged and uncertain intents enter tool-result verification and the same 120-second deadline. Exact completed-tool evidence can resolve a lost reply without resending; absence of evidence becomes a bounded incident. Successful native response is separate from tool success, output completion and supervisor acceptance. A correlated completed tool-call event is required for post-write verification of canonical path, regular-file identity, link count, size and expected content hash. Until that verification completes, the root pool cannot authorize another response. Missing/failed tool evidence or a changed path/content revokes the grant and records an incident for the supervisor and phone interface. This detects a filesystem race; it does not undo or claim to prevent an already executed out-of-scope write. Escalated and uncertain prompts wake the existing supervisor with exact evidence; routine responses are recorded without an unnecessary model wake.

## Release and rollback

Preserve current server IDs, credentials, saved sessions and MCP paths. Before native module changes stop only the verified owned controller/Paseo processes, with all enrolled sessions human and native work idle. Build and independently review an immutable controller release and native module overlay; verify actual loaded receipt and new boot after restart. One new permission-overlay manifest is authoritative for this upgrade: its base is the exact currently installed guard-patched module bytes (source 768190e), its target is the exact permission-patched bytes, and it includes old/new guard paths and hashes, old/new active.json bytes, dependency after-side tree identity and both tree fingerprints. Vendor-original admission-base.json and .original backups are retained provenance, never this overlay rollback target. The legacy deploy-admission rollback is not used. The dependency switch record pins full tree contents: native overlay deployment must durably record old/new module hashes and the old/new after-tree fingerprint under the dependency lock, with an in-progress state refusing launcher startup until finalized. The ordered state machine is prepared -> dependency-startup-blocked -> module/guard/active-manifest writes -> verified target fingerprint -> complete; every boundary is durable and recoverable. Recovery restores exact known old overlay bytes and old active.json or completes exact known new bytes and new active.json before updating the fingerprint. Unknown bytes refuse recovery. Preparation, movement and completion also verify the installed root package and lock metadata against the repaired dependency side. Overlay rollback always restores the previous guard-patched base, never vendor originals. The supported dependency switch must refuse rollback to its before side while a permission-overlay marker is active; first roll back this overlay, then switch dependencies and use the matching old controller. The retained original dependency tree is not patched. The original dependency tree stays unchanged; whole-platform rollback restores the matching old guard/controller and dependency record, never older session history. No bypass of fingerprint checks or unexplained direct record edit.

Fix the previously reviewed operation-record producer defect: persist only PID/start identities, retain verbose diagnostics externally, and reject encoded records over the consumer's 8,192-byte cap before writing.

## Evidence

Tests hold a controller write transaction while native read-only admission runs, race a human response/message/stop clearing a prompt, exhaust the shared quota across parent and worker, and swap a symlink before post-write verification to assert revocation and incident evidence. Tests also cover actual policy boundaries, two prompt identities and changed input, duplicate/reconnect delivery, scope escalation, stale grant/parent/link generations, native human-response race, native reboot, uncertain provider reply, journal crash/reopen and quota. Preserve existing controller tests. Rehearse overlay apply/recovery/rollback while stopped and reject unknown bytes. Installed acceptance uses real saved native sessions, two distinct Write/Edit prompts authorized by the handler, current-turn tool results and an independent supervisor review, with no manual permission response or nudge. Verify the phone grant/status/revoke view at 390px and existing navigation. Physical-phone interaction is not inferred from viewport testing.

General provider-specific approval kinds, cross-host ownership transfer, task-board generalization and the remaining full-platform ADW gates continue as separate required increments of the full goal.

Decision record: broad provider accept-edits modes would bypass exact per-request review and evidence; model-driven handling would waste wake-ups for routine tools. The existing observer plus a small read-only native guard is the chosen boundary. The blast radius is the owned mini controller, additive journal tables, private plugin and four existing guard-patched native modules. Native intent state is pending -> one-shot admitted in memory -> controller acknowledged/refused/uncertain -> separately verified tool result; no transition retries an old response. Same-user host processes remain trusted.

Verification liveness decision: the gate covers the shared pool, while independent root pools continue. A completed tool event plus matching file releases it. A failed/cancelled tool, caught-up terminal timeline without the event, changed native identity, or 120 seconds without verification records an incident and revokes the root grant. The phone shows the pending count and incident; a linked supervisor receives an event-driven wake. The 30-second runtime watchdog covers missed native events, so timeout notification may arrive up to one watchdog interval after the deadline. Conservative revocation requires an explicit new grant; it does not silently widen authority to keep a stalled organization moving.
