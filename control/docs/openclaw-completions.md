# OpenClaw completion continuations

This increment lets an explicitly bound saved OpenClaw conversation wake when its delegated worker finishes, read the correlated output, choose at most one follow-up, and durably acknowledge consumption. It uses the existing Fulcra delivery journal and native event subscription, plus OpenClaw's public injection and targeted heartbeat APIs. Source checks, installed behavior and independent acceptance are separate claims; the source alone does not establish rollout.

## Authority and continuity

The plugin's optional `completionWakes: true` enables its service and correlation hooks. Default is disabled. Existing `bindingsDir` and `agentId` remain required, with private operator-written bindings to a current per-worker grant. The existing conversation/prompt hook grants remain required. The agent's exact native tool allowlist is status, assign, result and ack. Other agents are unchanged.

A host turn must have trigger `heartbeat`, channel ID `heartbeat`, no sender or incoming channel, and exactly one injection owned by this plugin. That injection must match a pending controller notification, original conversation key and UUID, worker delegation generation and origin hash. The actual host run ID and MCP call ID are joined through `agent_turn_prepare` and `before_tool_call`; execute must consume the ticket for precisely that tool and argument digest. Model arguments cannot choose the origin, worker, run or notification. Tickets expire after three minutes and are cleared at run end, cancellation or a later turn in the conversation. A user/channel turn that drains an injection receives no background ticket; the durable pending completion can be queued again later. No fabricated `senderIsOwner` field is used.

OpenClaw may cold-load a separate tool registry from its running service registry. All hook and factory registrations therefore resolve the one started service for the exact source module path and configuration (binding directory, agent, trusted owner key and wake opt-in). The process-local registry is bounded to 32 active services, rejects duplicate starts, removes authority before stop and cleans up failed starts. A discovery-only registration cannot replace the active service. Module copies with the same source URL path share that lease; a different release path or configuration does not. This registry holds only existing service/ticket references, with no new task or delivery state.

Worker identity, current prompt, task authority and capability are rechecked around asynchronous observations and at native admission. Human takeover revokes further access, including cached output. Removing a binding alone cannot retract an already admitted instruction; revoke native delegation first. The plugin never receives Paseo or operator credentials and does not implement another completion detector.

Saved OpenClaw key/UUID and the worker's native identity are retained. OpenClaw may rotate its own underlying Claude handle when its message policy changes between owner and background turns. Keep both handles and the reason in evidence, and verify substantive context continuity. Do not disable message-policy isolation to keep one handle. Each wake carries the original controller instruction, with the latest follow-up excerpt where applicable; this is scoped task context, not a substitute for shared canonical decisions.

## Durable disposition

The controller prepares a notification only from its existing correlated result reader after the turn ended. Its existing delivery result JSON retains the bounded output and evidence hash, original instruction, origin, generation, attempts and timestamps. No database table or schema migration is introduced. An ended turn with no text retains `outputObserved: false` and a null hash; it is not rewritten as successful output.

The supervisor reads this cached result before assigning or acknowledging. One follow-up ID and its first chosen instruction are persisted before dispatch. A retry, including differently worded retry text, reuses that exact ID/instruction and native receipt. Once that follow-up becomes the current prompt, the previous output remains readable through its notification. This closes the interruption window between follow-up admission and acknowledgment. Acknowledgment requires the exact read evidence hash, including null only for an actually empty result, and refuses an unresolved follow-up. It records consumption, never independent acceptance. A later completed follow-up creates its own notification and inherits the original task instruction.

Inspect projects notification metadata only, retaining output in the journal for its scoped result RPC; accumulated previews must not overflow the socket response. Both socket clients decode UTF-8 as a stream so packet boundaries cannot corrupt output.

Current inspection and ingress status explicitly project an unconsumed notification as `superseded` when the owner has moved to another input, with the observed replacement ID, or `previous-generation` after takeover/handback. These are current observations, not fabricated consumption or historical transition timestamps; the retained notification is unchanged. Preparing a completion from an older delegation returns non-ready without output or a repeated service failure. Its cached read, assignment and acknowledgment still refuse under the new generation. The current delivery can create its own completion normally.

## Waiting, retry and limits

The service uses `notify-wait`, backed by actual native subscriptions with a twenty-second runtime watchdog. It does not wake a model to poll. A private directory watch discovers bindings, with a thirty-second runtime reconciliation fallback. Limits are 32 bindings and controller waiters, 32 active ticket runs, 128 outstanding call tickets and 128 seen call IDs per run. Existing journal capacity also applies. These are bounded resource limits, not a claim of portfolio fairness or indefinite archival.

Before enqueue, a durable claim reserves one of five attempts and the next eligible time four minutes later. Injection TTL is five minutes with the notification UUID as its idempotency key. The exact public heartbeat tuple is `source: notifications-event`, `intent: immediate`, `reason: wake`, explicit agent and saved session key, with `heartbeat.target: none`. A local plugin cannot rely on bundled-only session scheduling; custom reasons/event intent do not establish a wake. Binding changes after enqueue prevent requesting a heartbeat, and later host validation rejects stale queued work. Retry exhaustion appears in the retained record and service failure health; an operator must inspect it. No silent infinite model retry occurs.

## Verification and rollout

Tests exercise the real controller journal and native admission guard, cached output after follow-up, interrupted choice replay, actual native event subscriptions, authority revocation, empty output, bounded inspect payloads, split UTF-8 socket frames, actual private binding files, host hook correlation and stale asynchronous callbacks. Service tests identify their mocked transport explicitly.

Installed acceptance must separately show a real worker completion automatically waking the saved OpenClaw supervisor, actual result/follow-up/ack tool calls, interrupted continuation without repeated worker input, takeover refusal and context continuity across owner/background transitions. Initial activation belongs in an isolated Gateway with private synthetic task data and no external channel delivery. Main Gateway, Discord routing, autostart and full programme acceptance remain separate rollout obligations.

Use immutable controller/plugin bundles, current journal integrity and a stopped-process backup. Keep the native Paseo process and admission guard unchanged for this increment. Rollback disables the service and restores the previous source against the current journal, preserving newer receipts and output; never restore a historical database over subsequent work. The full ADW gate remains authoritative.
