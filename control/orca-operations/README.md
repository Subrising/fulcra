# Owner operational notices

The `ai.orca.health` launchd monitor runs every 30 seconds on the Mini. Its code and incident database live on the internal user volume, outside the watched queue volume. A probe has a five-second deadline. It checks the recorded heartbeat and whether that PID exists; this establishes liveness, not correctness of every queue item.

A heartbeat is stale at 60 seconds. A continuously unhealthy observation must persist another 60 seconds before a failure notice is committed and sent through the existing OpenClaw gateway to the owner-configured Discord channel, explicitly owned by `main`. Recovery generates a separate notice. There are no model turns, worker input or automatic service repairs. Detection is normally within 90–150 seconds of the last heartbeat; network/Gateway outages can prevent notification. Physical phone push and whole-machine/volume-loss acceptance are separate.

The private database is `~/.local/share/orca-health/state/monitor.sqlite`. `notices` retains incident ID, phase, committed intent and actual transport result. A crash or timeout after committed intent remains uncertain: inspect the exact message/incident before manual reconciliation; never blindly resend. `health` records the latest observation. The owner is the local-board operator. The monitor cannot detect its own failure while the entire machine or launchd is down.

Runbook: inspect `launchctl print gui/$(id -u)/ai.orca.health`, the private health database, `~/Library/Logs/Orca/health-error.log`, and the ordinary Fulcra `watches` result. Establish queue and native ownership before any recovery; do not replay a receipt because its callback is delayed. To roll back the monitor, boot out only `ai.orca.health` and retain its database/receipt. The existing watcher is `ai.orca.watch` and has separate ownership.

`node-runtime.json` and `prepare_runtime.py` reproduce the private Node runtime from the official checksummed archive plus integrity-pinned npm packages. Maintenance replaces only three same-major npm dependency versions with upstream patched releases. It does not update global Node, provider daemons or the MacBook. Recheck each dependency's version compatibility and rescan the installed inventory before accepting a new upstream version. Package advisories, binary/OS advisories and exploitability are separate assessments.

Decision record: use an independent local one-shot monitor because the watched process cannot alert when it has stopped. Reuse the existing Gateway send API with an explicit main owner; do not set a global default agent. The blast radius is one newly owned monitor, one owned conversation watcher runtime and the configured owner Discord channel. Other provider sessions and global runtimes remain unchanged. Same-user code/configuration and Gateway credentials are trusted; worker output is never a configuration input. State moves healthy → pending failure → committed incident → committed recovery; every transport intent is persisted before the send, and uncertain states require manual reconciliation. The private maintained npm tree carries integrity-pinned upstream patch releases; upgrading the whole global Node environment was rejected because it would affect unrelated providers.
